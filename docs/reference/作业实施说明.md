## 1. 最终要做成什么

完成一条可复现的处理链路：真实 CSV 数据 → 导入 IoTDB → SQL 调用自定义异常检测函数 → 输出异常分数 → 计算检测指标，并与数据库外运行的同一算法及其他基线比较。

最终成果不要求是带网页的完整产品。重点是：问题有真实依据、算法包含针对周期场景的改进、UDF 能运行、实验比较公平、过程和结果可以复现。先完成单变量、已知周期的版本，不增加深度学习、自动周期识别、多节点集群或可视化系统。

本说明是实施指南。安装、注册和查询命令供后续执行；拟建的模块、脚本及函数目前不代表已经存在。环境与源码信息已核对，但尚未安装 IoTDB、编译 UDF 或完成端到端运行。

### 4.2 时间、数据类型和清洗约定

源文件不标时区。采用统一的“无时区源时间按 UTC 坐标编码为 epoch 毫秒”的技术约定，使同一文本时间在两台机器上得到相同整数；这不表示原始业务时间真实属于 UTC，也不转换纽约夏令时。数据与事件窗口必须使用完全相同的编码，禁止使用依赖本机默认时区的 timestamp() 转换。

建议转换后的 CSV 字段为 timestamp_ms、source_timestamp、value。示例 2014-07-01 00:00:00 对应 1404172800000；Δ=1800000 毫秒。数据库时间精度固定为 ms，取值统一使用 DOUBLE。

保留原始 CSV 不变。预处理只做显式检查和格式转换：空值、非有限值、重复时间戳、乱序、非固定网格。该主数据在选题阶段未发现缺失或重复；若后续文件检查不同，要先查输入版本。不要先标准化整条序列、填补未来值、平滑异常或清除官方事件区间。

标签仅交给评价程序。检测核心和 UDF 不接收标签、不读取事件 JSON，也不根据某时刻属于节日而特殊放行。

### 4.3 IoTDB 存储设计

在树模型中存储一条序列即可：

```sql
CREATE DATABASE root.periodic_ad;
CREATE TIMESERIES root.periodic_ad.nyc.value
WITH DATATYPE=DOUBLE, ENCODING=PLAIN;
```

由 runner 的导入子命令使用 Java Session 按批写入，优先使用 Tablet；一次性 10,320 点的数据不值得引入分布式导入工具。先导入少量固定样本核对时间和数值，再导入全部。

导入后检查 COUNT(value)、首尾点及报告中的四个对照时刻；数量应为 10,320，数值应与 CSV 一致。保留导入日志、查询文本和数据哈希。后续重复写同一时间戳可能覆盖值，正式实验使用独立、固定数据路径，不混入测试数据。

## 5. 算法和 UDF 的输入输出契约

### 5.1 核心检测器

输入：按时间严格递增的 (timestampMs, value)，以及固定参数配置。核心维护 P 个相位缓冲区和一个残差窗口，按“读取旧状态 → 评分 → 更新相位状态 → 更新残差窗口”的顺序运行。

默认候选参数：P=336（周周期）、K=4、W=336；Δ=1800000；t0 固定为源序列起点；初次调试使用 τ=4、c=3。最后的 τ、c、K 通过验证段确定，不能将调试值直接称为最佳参数。P=48 作为预先规定的敏感性分析，不根据测试结果选择最有利周期。

公式沿用选题报告：b 为当前相位历史状态的中位数，r=x−b；m 和 a 分别由此前残差的中位数与缩放 MAD 得到；s=|r−m|/a。评分完成后将 x*=b+m+clip(r−m,−ca,ca) 入相位缓冲区，再将原始 r 入残差窗口。

预热严格采用报告中的三阶段规则：各相位收满 K 个有效原值 → 计算历史残差并收满 W 个有效值（先算残差，再加入原值）→ 从下一个有效点开始评分。无缺失且 K=4、P=W=336 时，前 1,680 点预热，后续 8,640 点可输出分数。尺度下限默认在预热结束时根据初始残差确定并冻结；测试和手工样例可显式指定正 ε。

核心内部结果可包含 score、flag、baseline、residual、scale、updatedValue，便于调试；这些调试字段不是要求 UDTF 同时返回的多列结果。

### 5.2 SQL UDTF

建议参数名称统一为 step_ms、origin_ms、period、history、residual_window、threshold、clip、epsilon、mode。epsilon 可选，未指定时按报告默认规则计算。参数含义、范围和默认值必须写入 README。

单次 SQL 调用只返回一列：mode=score 输出 DOUBLE 分数；mode=flag 输出 BOOLEAN 标记。预热和无效点不输出行。不在两个独立函数调用之间共享状态；若同时查询 score 与 flag，两次调用应独立且使用相同参数。

注册方案（构建并部署成功后执行）：

```bash
# 在自己的项目根目录构建，以下命令会运行本工程既有测试
mvn clean verify

# 将含 core 的最终 UDF JAR 复制到本地单节点实例
mkdir -p "$IOTDB_HOME/ext/udf"
# 实际 JAR 文件名由自己的 Maven 配置确定
cp detector-udf/target/periodic-ad-udf.jar "$IOTDB_HOME/ext/udf/"
```

```sql
CREATE FUNCTION periodic_ad
AS 'edu.course.periodicad.PeriodicAnomalyUDTF';
SHOW FUNCTIONS;
```

使用配置的 udf_lib_dir；默认是 ext/udf。不要仅凭课件中的某个示例路径把产物随意放进 tmp。若修改算法后替换 JAR，需要先 DROP FUNCTION periodic_ad，再更换本项目的 JAR 并重新注册；保留旧版本哈希，不删除其他函数文件。

查询示例（函数实现后才可执行）：

```sql
SELECT periodic_ad(value,
  'step_ms'='1800000',
  'origin_ms'='1404172800000',
  'period'='336', 'history'='4',
  'residual_window'='336',
  'threshold'='4', 'clip'='3',
  'mode'='score')
FROM root.periodic_ad.nyc
WHERE time >= 1404172800000
  AND time < 1422748800000;
```

查询应从共同的训练历史起点开始。不要用 WHERE time >= 测试起点直接截掉训练、验证状态，也不要加 value>某阈值过滤掉算法需要的历史点。评价程序在取得分数后再选择测试区间。SQL 不使用 LIMIT 提前截断结果，客户端必须完整消费结果集。

### 5.3 实验程序的文件输出

建议统一以下产物结构：

- scores.csv：timestamp_ms、source_timestamp、value、score、flag；只包含可评分点。
- debug.csv：可选，记录少量目标时段的 baseline、residual、scale、updatedValue；不在性能实验中逐点打印。
- events.csv：合并后的告警事件起止时间、匹配标签窗口、TP/FP/重复告警分类。
- metrics.json：事件计数、Precision、Recall、F1、窗口外告警率及方法配置标识。
- timings.csv：路径、重复编号、输入点数、输出点数、端到端耗时、可测的资源指标。
- config.json、environment.txt、run.log：还原本次运行所需的参数、版本与日志。

IoTDB 返回的单列分数由 runner 与原始数据按时间戳关联后生成 scores.csv。不要把“导出的 CSV 有五列”与“UDF 必须返回五列”混为一谈。

## 6. 按什么顺序做

### 阶段 A：先跑通最小数据库链路

完成 JDK/Maven 安装、启动 IoTDB、连接树模型、导入十余点样本；实现并注册简单透传 UDF。通过依据是：SQL 输出时间戳和值与预期一致，日志无本次相关异常。保留版本、构建日志和 SQL 结果。

这一阶段不做完整异常算法，也不下载大型预测模型。若失败，先解决依赖、JAR 内容、类名、模型类型和部署路径，不拿真实算法反复试环境。

### 阶段 B：完成数据核对与实验协议

获取并校验主数据和标签，生成数据清单、日/周周期统计、真实事件对照图；固定时间编码、数据划分、指标和告警合并规则。形成 docs/data.md 与 docs/experiment.md。

主数据划分：2014 年 7–8 月为训练；9 月 1 日至 10 月 15 日为验证；10 月 16 日至 2015 年 1 月 31 日为测试。边界按源时间约定转换，所有方法完全一致。

### 阶段 C：先实现数据库外核心，再封装

先写 detector-core 和 CSV 运行器，完成手算样例、常值、周期、尖峰、缺口和预热检查；再写三个更新版本：直接更新、异常冻结、有界更新。由同一核心配置选择版本，减少无关差异。

运行器从 CSV 顺序喂入数据，得到分数，不看标签。评分逻辑稳定后再接入 IoTDB UDTF；不要在 Java、Python、UDF 中分别维护三套不一致的主算法。

### 阶段 D：验证数据库内外一致性

对相同历史范围、参数和数据，比较 CSV/Java 核心、IoTDB UDF、数据库导出后 Java 核心的有效时间戳与分数。预设浮点容差，例如 |a−b|≤10^−9+10^−8×max(|a|,|b|)，并检查 NaN、漏点及顺序。

分数未对齐前不做性能结论。问题定位优先检查预热起点、时间精度、NULL 处理、状态是否跨查询错误共享和参数默认值。

### 阶段 E：选参、真实测试和机制分析

主方法先在训练与验证上选参；验证背景段每日至多 0.5 个告警事件作为预算，合成扰动只用于辅助选参。各候选必须从训练起点独立重放；选定后重新处理未经注入的训练和验证数据，再接续真实测试。

实现滑动 Z-score、滑动 MAD、固定周期检测器、直接更新周期检测器等基线。做机制消融时固定其他参数，仅改变周期项或更新策略；残差窗口的更新规则保持相同。

每次实验保存完整配置与原始计数。固定超参数方案后，主数据可对 K∈{3,4,6}、c∈{2,3,5}、τ∈{3,4,5,6} 形成至多 36 组周周期候选，不需要一开始扩大网格。测试结果不得回流重新挑选参数。

按报告的预设条件再补 2–3 条真实序列：真实来源、固定采样、训练至少覆盖 8 个候选周期、训练周期相关不低于 0.5。筛选时先检查长度和周期，不看算法测试成绩；为每条新序列单独写清时间划分和标签覆盖情况。

### 阶段 F：性能比较、结果分析与结题

在相同机器和同一数据实例比较 UDF 与外部 Java 执行；完成真实事件、合成诊断、基线、消融和规模实验。根据原始结果写报告，允许结论为“仅在某些场景有效”或“未取得预期收益”。提交前从干净构建产物验证一次 README 中的最短复现链路，无需反复全量构建官方仓库。

## 7. 具体怎么测试

### 7.1 最小正确性清单

- 常值序列：MAD=0 时不除零，不产生 NaN/Infinity。
- 完美周期：预热结束后分数接近 0。
- 单点尖峰：当前点评分在更新之前完成，不被自身吸收。
- 持续下降、缓慢漂移、永久阶跃：分别观察检出和适应，任务标签按场景明确。
- 缺失：按时间戳保持相位，预热不足时没有输出，不把行数当相位。
- 非法输入：拒绝非法参数、重复/非网格时间戳；原始乱序在导入前排序。
- 实例隔离：两次独立查询相同输入得到同样结果，不继承上一次的缓存。

已知手算样例：B=[10,10,10,10]、R=[−1,0,0,1]、x=14、ε=0.01、τ=4、c=3。应得到 MAD=0.5、scale=0.7413、score≈5.395926、flag=true、updatedValue=12.2239。该状态用于核心单元测试；不要通过尚不存在的 SQL 参数假装直接设置内部缓冲区。

端到端小数据可另外构造 P=4、K=3、W=4、Δ=1000 的 32 点周期序列，在完成前 16 点预热后加入一个尖峰，人工核对首个有效输出点及尖峰分数。

### 7.2 检测指标不要混口径

以官方窗口为事件标签。相邻告警点相隔不超过 1 小时合并为一件告警，以首次告警时间归属窗口；每个窗口最早开始的一件告警记 TP，后续同窗口告警记重复告警并计 FP；窗口外开始的告警计 FP；没有匹配告警的窗口计 FN。跨边界延续的事件仍按首次时间归属，不因后续进入窗口而重新记一次命中。

报告 Precision=TP/(TP+FP)、Recall=TP/(TP+FN)、F1=2TP/(2TP+FP+FN)，分母为零时记为 0。窗口外告警率使用窗口外总时长折算天数。该口径不等于 NAB 官方加权评分，论文/报告中应准确命名。

主序列只有五个事件，因此必须给五个窗口逐项命中情况及 TP/FP/FN，不只给一个 F1 数字。官方宽窗口不能当成精确故障起点；真实故障延迟只在有明确起点的注入实验中计算。

### 7.3 性能比较要回答什么

路径 A：客户端发起 UDF 查询，完整接收分数。路径 B：客户端查询同样范围的原始值，调用同一 Java 核心完成评分。从发起查询计时，到结果完全读取且必要计算结束为止。

输入历史和最终评分集合相同，不意味着网络返回行数相同：A 可省略预热行，B 必须读取原始预热输入。分别记录实际网络返回行数；无法可靠测量传输字节时只报告行数，不以 CSV 文件大小冒充协议传输量。

先进行 JVM/查询性能预热，再交替顺序运行至少 5 次；记录每次而不是只留最快值。这里的性能预热与算法的历史预热不同，两者均需记录。用中位数及离散程度报告端到端耗时，另记录外部纯计算耗时。若没有可靠的 UDF 内核计时，不编造“数据库内纯算法耗时”。

真实性能先用 10,320 点主序列，再用 10 万、100 万点的合成周期数据看扩展性；合成数据只证明规模表现，不作为新增真实异常证据。初版每点计算约 O(K log K+W log W)，记录 W 与 P，不把窗口变大后的耗时差异归因于数据库本身。
