1. 项目背景与目标

交通流量、业务访问量和设备读数，都可以表示为按时间排列的数值记录，这类数据称为时间序列。其中一些数据具有每天或每周重复的规律。异常检测的任务，是从这些记录中找出偏离日常规律的变化，供后续分析，而不是仅按数值高低划分正常与异常。

本项目面向周期长度已知、采样间隔固定、每个时刻只有一个数值的监测序列。判断一个新观测是否异常，需要先建立用于比较的正常水平，称为“基线”。基线应当反映当前周期位置的规律，也需要随长期变化更新；但异常观测反复进入历史，又可能改变基线，使后续异常不再显眼。这是本项目研究的主要问题。

项目同时完成算法与数据库实现：设计逐条处理数据的检测程序，并将它封装为 Apache IoTDB 的用户自定义函数（UDF）。IoTDB 用于存储按时间排列的监测记录；UDF 允许在 SQL 查询中调用自行编写的算法，使查询直接返回异常程度或告警标记。

仓库的主体是一套独立 Java 检测核心、一个 IoTDB 适配模块和一个数据库外运行程序。纽约出租车客流是后续实验使用的真实序列，不限定算法只能处理出租车数据。实验分别评价检测效果和数据库执行代价。

2. 方法来源与方案设计

2.1 周期分解与稳健统计

STL 是经典的时间序列分解方法，将序列拆分为趋势、季节项和余项。它为本项目提供的思路是：先解释重复出现的正常周期，再分析剩余偏差。RobustSTL 进一步讨论异常污染、周期波动和趋势变化，说明正常规律本身也可能改变。

本项目借鉴上述问题分析，采用适合逐条更新的轻量方案，而非复现这两种分解算法：为每个周期位置保存短历史，直接估计该位置的正常水平。中心与波动的估计采用中位数和中位绝对偏差（MAD），以减小少量极端值的影响。中位数取排序后的中间水平；MAD 衡量数据围绕中位数的典型偏差。

2.2 三个算法组成部分

组成部分作用
周期基线对照历史上相同周期位置的记录，保留正常的日内或周内差异。
稳健残差评分用观测值与周期基线的差估计近期偏移和波动，再衡量当前偏离程度。
有界历史更新允许正常水平变化，同时限制一次大幅偏离对同期历史的影响。

有界更新是本项目重点考察的策略。直接接收全部新值，可能逐渐吸收持续异常；拒绝所有高分观测，又可能妨碍正常水平变化。限幅策略在两者之间保留一定调整空间，其实际作用由后面的对照实验判断。

“自适应”具体指周期历史、近期偏移和波动尺度随数据更新；周期长度本身由场景知识或前段数据预先确定，不在每条观测到来时重新学习。

3. 周期感知自适应检测算法

检测器对每个有效观测完成三项工作：取出同一周期位置的历史作为参照，计算当前偏离程度，再更新历史。用于当前评分的全部状态，都来自当前点之前。

3.1 输入、参数与两份历史

输入是按时间升序排列的“时间戳 t、数值 x”。每个周期含 P 个采样位置，每个位置保存最近 K 个历史值；另外保存最近 W 个原始残差。周期位置也称“相位”，由时间戳计算，而不是按已读行数轮流编号。

符号含义本次真实实验
Δ、t₀采样间隔与固定时间起点，用来定位当前相位。30 分钟；2014-07-01 00:00 的源时间坐标
P一个周期中的采样位置数。336，即 7×24×2
K每个相位保留的历史值数量。6，即参考最近六个周周期
W近期原始残差窗口的长度。336
τ告警阈值，分数严格大于它才告警。4
c内部历史写回的限幅系数。2
ε波动尺度下限，避免常值窗口除以零。由预热残差自动确定，之后固定

例如，半小时采样、按周比较时，每周四 12:00 都进入同一个相位历史 B[p]。残差窗口 R 则不区分相位，保留所有时段最近的偏差。前者描述同期规律，后者描述近期整体偏移与波动。

3.2 初始化与逐点处理流程

程序开始时没有可用参照。它先收集各相位的 K 个值，再收集 W 个残差，这两个阶段称为预热，均不输出分数。完整、连续输入下需要 P×K+W 个采样点，下一点开始正式检测。

3.3 异常分数的计算

相位历史的中位数 b 是周期基线，r=x−b 是当前残差。近期残差的中位数 m 修正整体偏移，因此当前预测中心为 b+m。用残差的中位绝对偏差 MAD 估计波动尺度 a，再计算当前偏离相当于多少个这样的尺度。

周期定位p = floor((t − t₀) / Δ) mod P
周期基线b = median(B[p])
原始残差r = x − b
近期偏移m = median(R)
近期波动MAD(R) = median(|Rᵢ − m|)
波动尺度a = max(ε, 1.4826 × MAD(R))
分数与告警s = |r − m| / a；flag = (s > τ)

median 表示中位数。系数 1.4826 使 MAD 在近似正态波动下具有标准差的尺度。分数越大，当前偏离相对于近期波动越明显；它不是异常概率。告警标记只指出需要检查的时刻，不判断变化的业务原因。

3.4 三种历史更新策略

评分完成后，直接更新将 x 原样写入当前相位历史；冻结更新仅在本次未告警时写入；有界更新则以预测中心为起点，最多向当前值方向移动 c×a，再把得到的 x* 写入。c 限制学习幅度，τ 控制是否告警，二者各有作用。

x* = b + m + clip(r − m, −c×a, c×a)

clip(v, L, U) = max(L, min(U, v))

三种策略均将原始残差 r 写入 R，不把限幅后的残差写入。限幅只影响检测器内部的相位历史，原始输入记录保持不变。

3.6 主方法伪代码

下面完整列出周期方法的处理路径。输入时间与数值已通过检查；B[p] 和 R 都是写满后淘汰最旧值的有限长度缓冲区。

输入：当前时间 t、观测 x；旧状态 B[0…P−1]、R
p ← 当前时间对应的周期位置

若任一相位历史未满：
    将 x 加入 B[p]
    返回空结果

b ← median(B[p])
r ← x − b
若 R 未满：
    将 r 加入 R，将 x 加入 B[p]
    若 R 刚好存满：确定自动尺度下限 ε
    返回空结果

m ← median(R)
a ← max(ε, 1.4826 × MAD(R))
s ← |r − m| / a
flag ← (s > τ)

直接策略：将 x 加入 B[p]
冻结策略：仅在 flag 为 false 时将 x 加入 B[p]
有界策略：将 b+m+clip(r−m, −c×a, c×a) 加入 B[p]
三种策略均将原始 r 加入 R
返回当前时间、原值、基线、尺度、分数、告警及写回值

空值和非有限值不进入历史。时间戳必须递增并位于采样网格上，允许有整数倍采样间隔的缺口；缺口不会使相位错位，但可能延长预热。自动尺度下限取 max(10⁻⁹, 10⁻³×1.4826×MAD(R初始))，随后固定使用。

5. 实验数据与评价设计

5.1 真实序列与周期配置

检测质量使用公开异常检测数据集 NAB 的纽约出租车序列评价。每条记录为半小时内的乘客总数，共 10,320 条，覆盖 2014 年 7 月 1 日至 2015 年 1 月 31 日。训练段中，周滞后相关系数约为 0.967，高于日滞后的 0.848，因此主实验采用周周期 P=336。

下图用两个星期四说明这条序列的变化。11 月 27 日 12:00 的客流为 13,282，比前一周同一时刻的 18,309 少了约 27.5%。算法实际参考多周历史，这个两日对照只用于展示数据特征。

数据按时间分为三段：7–8 月建立初始历史，9 月 1 日至 10 月 15 日用于选参，10 月 16 日至次年 1 月 31 日用于最终评价。验证段没有官方异常窗口，使用背景数据和预设扰动副本辅助校准；选定参数后，从原始数据重新重放，再接续评价段，不继承扰动副本的状态。

主方法最终使用 P=W=336、K=6、τ=4、c=2。在完整输入下，前 2,352 点用于预热，随后输出 7,968 条结果；最终评价段有 5,184 点，全部处于正式输出阶段。

5.2 标注事件与告警计数

NAB 数据说明将五段异常变化关联到纽约马拉松、感恩节、圣诞节、新年和暴风雪。这里的异常是偏离通常客流规律，不等同于交通系统故障。数据集为这些变化提供异常时间范围，称为“标注窗口”；本项目将每个窗口作为一个待检出的标注事件。

标注只用于评价，算法不读取它们。窗口表示异常的大致评价范围，并非精确起点，也不表示其中每个采样点都异常。一个采样点分数超过阈值，形成一个告警点；相邻间隔不超过 1 小时的告警点合并成一次告警事件。后文的告警次数均按合并后的事件计数。

以每次告警的开始时刻与窗口匹配：某窗口内的第一次告警计为命中，同一窗口内后来再次开始的告警计为重复告警，所有窗口之外开始的告警计为窗口外告警。重复与窗口外两类在本项目规则中计为误报。

5.3 算法对照与系统比较

算法对照包括有界更新、直接更新、训练后固定的周期模型，以及不区分周期位置的滑动中位数和滑动均值方法。各方法分别在验证阶段选参，在相同评价区间比较。为单独分析机制，还固定主方法参数，分别去掉周期项或替换更新策略，这类只改一个环节的比较称为消融实验。

评价同时考虑找到多少标注事件和发出多少误报。综合指标 F1 结合“告警中有多少为有效命中”和“应找事件中找到多少”两个比例，越高越好；逐事件原始计数一并保留。这里采用基于官方窗口的自定义计数，不是 NAB 官方加权得分。

TP = 首次命中数；FP = 重复告警数 + 窗口外告警数；FN = 未命中窗口数

Precision = TP/(TP+FP)；Recall = TP/(TP+FN)

F1 = 2×Precision×Recall/(Precision+Recall)

系统比较使用同一 Java 核心的两条路径：A 在 IoTDB 内计算并返回分数；B 先从 IoTDB 取回原始值，再在外部 Java 程序中计算。两者均从发出查询计时，到完整消费结果并完成计算为止。使用真实的 10,320 点序列，以及 10 万、100 万点的合成周期序列，预热两轮后记录五轮交替运行的耗时中位数，计时不含数据导入与结果落盘；后两种规模用于考察执行代价。

6. 实验结果与分析

6.1 事件检出与误报

下图展示感恩节前后的实际输出：上半图比较观测与预测中心，下半图展示分数及阈值。蓝点表示逐点告警，浅蓝色带表示官方标注窗口；它们与随后按事件汇总的计数不同。

有界更新在五个标注窗口内都发出了告警。总计 34 次告警中，5 次为首次命中，17 次是在已命中窗口内再次开始的告警，12 次开始于所有窗口之外。因此，五段已知变化虽然都被找到，按当前评价规则仍有 29 次误报。

分别选参时，有界更新比直接更新少两次误报，改善较小。滑动中位数只发出一次告警且恰好命中一次，虽然漏掉另外四段变化，F1 仍为 0.333，高于有界更新的 0.256。这表明只报告“找到全部事件”不足以描述实际告警质量。

6.2 周期项与更新策略的作用

固定主参数后，去掉周期项的版本没有命中这五个窗口；保留周期项、仅将直接更新改为有界更新，则只少一次窗口外告警。与分别选参的对照结合看，本次结果主要支持周期参照的作用，有界更新的额外改善有限。

受控的永久下降实验中，直接、冻结和有界更新最终都适应了新水平。原因之一是三种策略的残差窗口都继续接收原始残差，近期中心仍会改变。因此，限制相位历史的更新并不能单独保证对持续异常一直告警。

6.3 数据库内外执行结果

真实序列在数据库内外均产生 7,968 条正式结果，时间戳、异常分数和告警标记一致，说明两种入口复用了相同检测行为。耗时比较则是另一项结果：本机三组数据上，数据库内计算都比取回原值后计算更慢。

百万点时，数据库内计算约慢 6.3%。当前方案逐点返回分数，仍会产生接近输入规模的结果，未形成明显的返回数据量缩减。项目实现了查询中的检测功能，但在本次执行方式和环境下没有观察到提速。

7. 结论与后续工作

项目完成了周期参照、稳健残差评分与有界更新的组合实现，并通过独立核心和 UDF 适配层提供了文件重放与 IoTDB 查询两种入口。实验显示，周期参照有助于覆盖这条真实序列中的已知变化；有界更新只带来小幅误报改善，尚未解决重复告警与持续变化的适应问题。数据库接入提供了 SQL 调用能力，没有在本机比较中取得速度收益。

检测质量目前仅由一条真实序列评价。另筛选的 13 条候选未满足固定采样结构要求，没有纳入检测比较，因此结论还不能推广到更多数据。后续应优先完善告警事件状态，减少同一变化的重复提示，并结合任务需求决定长期变化应持续提示还是逐渐接受为新常态。
